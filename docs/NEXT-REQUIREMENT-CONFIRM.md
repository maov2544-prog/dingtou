## 2. 逐步拆解

### 步骤 1 · RPA 启动前置校验

**触发**：商务在企微群 @机器人 发送指定投放命令。

**断点续传规则（我理解的）**：

| # | 规则 |
|---|---|
| 1 | 商务 @机器人发指令 → RPA 记录**本次 @消息**，作为**本次结束标记** |
| 2 | 读取**上一次 @机器人指令记录**，作为**上次起始标记** |
| 3 | **审核区间** = 「上次 @消息」之后第一条视频链接 ～ 「本次 @消息」之前最后一条视频链接 |
| 4 | 逐条循环审核区间内**全部**视频链接；**单条失败不中断本轮**其余链接；本轮全部处理完后，**保存本次 @消息**作为下一轮的起始标记 |

**区间内逐条处理（3 道关卡，任一不过就 @达人 报错并跳到下一条）**：

| 顺序 | 动作 | 不通过时 |
|---|---|---|
| ① | 提取达人**抖音号**，回填到**企微达人昵称备注**（写入抖音号），方便后续管理 | — |
| ② | 解析视频**挂的商品 ID**，对照【**商品 id 映射表**】校验是否**主推链接** | ❌ 企微群 @达人：**「挂车链接有误，请联系对接商务处理」** → 继续下一条 |
| ③ | 调接口查该达人对该商品的**定向商品 + 佣金比例** | ❌ 查不到定向 / 佣金≠5% → @达人：**「链接定向有误，请联系对接商务处理」** → 继续下一条 |
| ✅ | 佣金 **= 5%** | RPA 把这条素材信息**完整填入【定投素材表】所有字段**，供商务第二轮人工审核 |

### 步骤 2 · 商务第二轮审核（视频内容合规）

- 商务打开【定投素材表】，**逐条**看填入的视频链接，**人工**审核视频内容是否可投放。
- ❌ **不合规** → 商务在表格对应字段填「**不投放原因**」→ RPA **定时抓取**该字段 → 企微群 @达人 告知原因。
- ✅ **合规** → 商务在表格对应字段填「**可投放**」→ RPA 抓取该状态 → **进入投放执行环节**。

> ✅ **老板 9/30 09:32 答复**：「**可投放 / 不投放原因**」= **在【定投素材表】新增两列**（现有 14 列里没有这两个字段）。

## 2.5 【定投素材表】的状态机与处理范围

**老板 9/30 09:32 + 09:41 口述，我整理：**

> 「先 RPA + 代码获取视频链接信息、ID 等等这些内容**写入表格**，**状态设置为待审核**，推给商务审核；
> 然后等到**审核通过后再把状态换成待投放**；**代码决定投放的地方**；**投随心推才是在表格中填「全域随心推」**。」
>
> 「**把备注改成投放状态**。里面这么多条数据不是每一条都要投放的，**只有投放状态为待投放的才需要进入随心推订单数检测去投放**；
> **投放类型这时候应该为空**；**投放类型不为空的都是老数据，不用管**。」

### 列改名

| 原列 | 改后 | 说明 |
|---|---|---|
| `N 投放备注` | **`投放状态`** | 现有值 `已投` 3438 / 空 1554；后续新增 `待审核` / `待投放` |

### 状态流转

```
   [新建行]  RPA + 代码 写入 视频链接 / ID / 商品 / 达人
       ▼
   投放状态 = 待审核  ──推给商务──►  商务人工审视频内容合规
       │                                    │
       │ 合规：填「可投放」                    │ 不合规：填「不投放原因」
       ▼                                    ▼
   投放状态 = 待投放                    终止 → @达人 告知原因
       │  此时 K 投放类型 应为空
       │
       │  ──►【随心推订单数检测】──► 代码决策 A/B/C1/C2 ──► 投放
       ▼
   投放状态 = 已投（回填投放字段；A 场景投随心推则 K 填「全域随心推」）
       │
       ▼
   步骤 4：批量扫「已投」→ 合并一条消息批量 @达人
```

### ⚠️ 处理范围（关键）

| 行的类型 | 特征 | 处理？ |
|---|---|---|
| **新数据** | `投放状态 = 待投放` 且 **`K 投放类型` 为空** | ✅ **要处理** → 进【随心推订单数检测】→ 投放 |
| **老数据** | **`K 投放类型` 非空**（`全域随心推` 3682 / `全域PC` 1303 / `待授权` 5） | ❌ **不用管**（已投过） |
| 待审核 | `投放状态 = 待审核` | 等商务审，暂不投放 |
| 已投 | `投放状态 = 已投` | 供步骤 4 批量通知 |

### 字段性质

| 字段 | 性质 | 谁写 |
|---|---|---|
| 视频链接 / 视频 ID / 商品 / 达人… | **输入** | RPA + 代码（步骤 1） |
| `投放状态`（待审核 → 待投放 → 已投） | **流程字段** | 代码 / RPA |
| 可投放 / 不投放原因 | **新增两列** | 商务 |
| **`K 投放类型`** | ⚠️ **输出字段** —— 投放后由代码回填（投随心推才填「全域随心推」）；**非空 = 老数据** | 代码 |

### 步骤 3 · RPA 执行投放（★ 核心，唯一明确要 Java 开发的部分）

1. RPA **同时读取【定投素材表】+【历史随心推订单存量表】**，按【**达人 + 商品**】维度**合并统计累计随心推计划总笔数**；
   同时**用接口校验**：该【达人 + 商品】**是否已经存在对应的千川计划**。

> 🔑 **老板 9/30 09:24 补充（关键）**：
> 「同时读取两表」这一步**只是为了判断是否 ≥ 3**；**后面的步骤用【随心推接口】获取订单数就可以了**。
>
> → 即 **N 是两段式确定的**：
> | 阶段 | 手段 | 作用 |
> |---|---|---|
> | **预筛** | 合并两表统计 | **廉价**，只为判断「是否 ≥ 3」 |
> | **精算** | **调随心推接口取订单数** | **权威计数源**，用来区分 `=3`(B) 与 `>3`(C1/C2) |
>
> 我据此**推断**的分支（待确认）：两表算出 `< 3` → 直接走 **A**（不调接口）；
> 两表算出 `≥ 3` → **调随心推接口**取准确笔数 → 再判 **B(=3)** / **C1** / **C2**。

| 场景 | 条件 | 动作 |
|---|---|---|
| **A** | 累计随心推笔数 **< 3** | RPA **新建随心推计划**；投放完成后**写入定投素材表** |
| **B** | 累计随心推笔数 **= 3** | 第 3 条随心推计划**已完成状态** → RPA 在**对应投放账户**新建**千川计划**，添加**所有视频素材**；命名 `抖音号-商品-新建计划日期MD` |
| **C1** | 累计随心推笔数 **> 3** 且**已存在**千川计划 | RPA 直接在该千川计划**新增本条视频素材**，**更新计划名称**（日期改为最新 `M.D`） |
| **C2** | 累计随心推笔数 **> 3** 且**不存在**千川计划（历史存量就超 3 笔，但之前没建） | RPA **直接新建千川计划**，添加**所有视频素材**；命名同上 |

2. 投放操作完成后：RPA **自动回填【定投素材表】**，更新投放相关字段；**循环读取下一条【可投放】素材**，直到全部处理完。

### 步骤 4 · RPA 分批统一通知达人（防刷屏）

RPA 按**设定时间段**批量扫描【定投素材表】，筛选所有**投放完成**的记录，
**合并为一条消息**，一次性批量 @全部已投放达人，统一告知视频已投放，避免群内逐条刷屏。

### 步骤 5 · 定投素材表持续累计监控

RPA **每次执行投放前**都会读取【定投素材表】+【历史随心推订单存量表】合并统计随心推笔数，
并**持续校验**【达人 + 商品】是否已有千川计划。

> **一旦千川计划创建完成**，后续同达人同商品的**新素材全部复用这个千川计划新增视频**，
> **不再新建随心推、不再重复新建千川计划**。

## 5. 核心指标 N 的定义

> **N = 该【达人(抖音号) + 商品】的累计随心推笔数**
> **两段式**：① 合并【定投素材表】+【历史随心推订单存量表】统计 → **只用于判断是否 ≥ 3**（预筛）
> 　　　　　② **调【随心推接口】取订单数** → **权威笔数**，用于区分 `=3` / `>3`

**为什么这样设计（我的理解）**：读 Excel 便宜但不一定准/新；接口准确但要花调用配额。
先用表预筛掉绝大多数 `< 3` 的组合（实测占 **81.77%**：N=1 59.93% + N=2 21.84%），
只有可能达标的（`≥ 3`，实测 **18.23%**）才值得调接口精算。

> ✅ **老板 9/30 09:32**：预筛时 **`K 投放类型` 不做筛选** —— 那张表只是**记录要投放的信息**，
> 预筛就是数该【达人+商品】的行数。若预筛把「全域PC」也算进来导致**偏高**，也无所谓：
> 预筛**偏保守**只是多调几次接口，**不影响最终结果**（权威笔数由随心推接口给）。
>
> ✅ **老板 9/30 09:41（处理范围）**：**只有 `投放状态 = 待投放` 且 `K 投放类型` 为空的行**
> 才进入「**随心推订单数检测**」并执行投放；`K 投放类型` 非空的都是**老数据，不用管**。
>
> ⚠️ **仍待确认（1 条）**：预筛到底数「**全部行数**」还是「**`K 投放类型` 非空（= 已投放）的行数**」？
> 两种读法都能实现，但算出的 N 不同。**我建议后者**（只有已投放的才算笔数），
> 并做成**配置项** `prescreen.scope = ALL | INVESTED` —— 口径要改时改配置，不改代码。

## 9.5 🔑 随心推订单数从哪来（已查 SDK 1.1.96，结论：**必须本地缓存**）

**老板 9/30 09:50 问**：不用表格预筛、直接调接口查订单数，接口压力大吗？每天拉一次全量存本地会不会更好？

### 实测结论：**「按达人+商品直接查订单数」的接口不存在**

我把 SDK 里所有「随心推订单」相关接口的过滤条件都 javap 出来了：

| API | 过滤条件 | 能否按达人/商品查 |
|---|---|---|
| **`QianchuanAwemeUniPromotionOrderGetV10Api`**（查随心推订单） | `orderCreateStartDate` / `orderCreateEndDate` / `status` | ❌ **不能** |
| `QianchuanAwemeOrderGetV10Api` | `marketingGoal` / `status` | ❌ 不能 |
| `QianchuanAwemeReportOrderGetV10Api` | `adIds` | ❌ 不能 |
| `QianchuanReportLongTransferOrderGetV10Api` | `adId` | ❌ 不能 |

→ **所有订单查询接口都只能按「时间窗 + 状态（+ 账户）」拉列表，没有达人/商品维度。**

**所以「不用预筛、直接逐条调接口查订单数」这条路技术上是走不通的** —— 不是压力大小的问题，是**根本没有这个入参**。

### 唯一可行方案 = 老板说的「拉下来存本地」

`QianchuanAwemeUniPromotionOrderGetV10Api` 的能力（javap 实测）：

| 项 | 值 |
|---|---|
| 入参 | `advertiserId` + `marketingGoal` + `filtering` + `orderField` + `page` + `count` |
| `filtering` | `orderCreateStartDate` / `orderCreateEndDate` / `status` —— ✅ **支持时间窗** |
| `count` 枚举 | **10 / 20 / 50**（单页最多 50，需翻页） |
| 返回每条订单 | `orderId` / `orderCreateTime` / `status` / `adId` / `supportAddBudget` |
| ↳ 达人 | `awemeInfo{ awemeId, awemeName, **awemeShowId** }` ← **抖音号** |
| ↳ 商品 | `productInfo{ **productId**, productName }` ← **商品 ID + 名称** |
| ↳ 指标 | `statsInfo` |

→ **返回里直接带「抖音号 + 商品 ID」**，本地按 `awemeShowId + productId` 分组计数 = **N**。完美对上需求。

### ✅ 我推荐的方案（三层）

```
① 本地订单快照（JSONL / SQLite）
     (抖音号, 商品ID) → 订单数、订单ID列表、最后更新时间

② 每日定时刷新（每天 1 次，固定时间）
     for 账户 in 投放账户信息表(8 个):
         QianchuanAwemeUniPromotionOrderGetV10Api(
             advertiserId = 账户,
             filtering.orderCreateStartDate/EndDate = 时间窗,
             count = 50, 翻页拉完 )
     → 本地按 awemeShowId + productId 聚合 → 覆盖快照

③ 投放前查本地快照（0 次接口调用）→ 得到 N
     快照缺失 / 过期 → 兜底触发一次刷新
```

**接口量估算**：每天 1 轮 × 8 个账户 × 页数。
若每账户 500 单 → 10 页 → **约 80 次调用/天**。可预测、可限速。

**比「每条待投放都查」小得多**，而且不会随待投放量线性增长。

### ⚠️ 两个必须注意的风险

1. **频控**：巨量平台有 `40130 / 40110 / 40100` 三层频控 + **5 分钟惩罚**。
   每日刷新必须**限速 + 指数退避重试**。老项目 `D:\program\aolandai\OceanEngine` 有现成实现，**要迁过来**。
2. **订单状态会变**（如取消/关停）→ 不能用「纯追加」。
   建议**滚动窗口覆盖**：每次重拉最近 N 天（如 30 天）覆盖旧记录，而不是只追加增量。

这也让【历史随心推订单存量表】的身份清楚了 —— **它应该就是「每天从接口拉下来、存到本地的这份订单数据」**。
