## 二、逐项验收

### 1️⃣ N 计数白名单

**口径**（老板定）：
```
算 N（7 个）：DELIVERY_OK / FROZEN / FINISHED / OVER / AUDIT / BOOK / CREATING
不算（5 个）：OFFLINE_AUDIT / FAILED / TIMEOUT / UNPAID / UNPAIDCANCEL
```

**实现**：`OrderSnapshotService` 用 **EnumSet 白名单**，`aggregate()` 里只有白名单内的订单才进 `orderIds`。

**为什么用白名单**：接口以后新增状态时，白名单默认**不算** → 最多晚建计划；
黑名单默认**算** → 会多算 N → 提前建计划 = **白花钱**。失效方向上前者便宜得多。

**验收点**：单测覆盖「白名单内计入 / 白名单外不计入」。

---

### 2️⃣ 互斥口径按场景分开（⚠️ 本轮最重要的口径修正）

**老板澄清**：
| 动作 | 受哪些状态限制 |
|---|---|
| 创建**随心推订单** | **5 个互斥状态**（`DELIVERY_OK`/`AUDIT`/`CREATING`/`BOOK`/`FROZEN`） |
| 创建**千川乘方计划** | **只判 `DELIVERY_OK`** —— 同一抖音号 × 同一商品维度下，无论随心推什么状态基本都能建成功；判投放中只是「想让它跑完再建」 |

**实现**：判断**从决策前移到决策后**，按场景分：
```java
boolean mustWait = switch (decision.scenario()) {
    case A -> countResult.blocked();        // 建随心推 → 5 状态
    case B, C1, C2 -> countResult.delivering();  // 建计划 → 只判投放中
};
```

**验收点**：`DefaultCumulativeCountServiceTest` 覆盖 `blocked` / `delivering` 两个标记。

### 4️⃣ 查计划排除 `DELETE`/`OFFLINE_AUDIT`

⚠️ **踩坑并纠正**：老板口述是 `DELETED`，但 `javap` 核对 SDK 1.1.96 后，
计划状态枚举的**实际值是 `DELETE`**（没有 `DELETED`）。已按实际值实现。

**🔴 顺带修了一个真 bug**：`PlanInfo.isDelivering()` 原来写的是
`status.contains("DELIVERY")` —— 而计划状态枚举里有 **`DAILY_DELIVERY_SECONDS_DONE`**
（当日投放时长跑完），**会被误判成「投放中」**。已改成精确匹配 `DELIVERY_OK`。

### 8️⃣ A：服务直接写素材表

**老板定**：像交付状态表/异常表那样，带备份。

| 项 | 实现 |
|---|---|
| 写入 | 只改**指定单元格**（K 投放类型 / N 投放状态），**不新建/删行、不动别的列** |

⚠️ **重要约束**：开了之后**影刀就不该再写素材表**，否则两边互相覆盖。切换时要确认影刀已停。

### 9️⃣ ②：定时轮询（不用影刀 POST）

**老板需求**：「做成轮询的，不用 post 来调度」。

**实现**：`PendingDeliveryScheduler`，`@Scheduled(cron = ...)`：
```
读素材表待投放行 → 跑 processPending → 直写回素材表
```

| 防护 | 实现 |
|---|---|
| **默认关** | `dingtou.scheduler.pending-enabled=false` |
| **防重入** | `AtomicBoolean` —— 上一轮没跑完不启动下一轮 |
| **当天不重复** | 「投放中 M.D」且 M.D == 今天 → 跳过；日期 < 今天 → 重新处理（自动顺延） |
| **异常不打死调度** | 整轮 try-catch（未捕获异常会让 Spring 调度器静默停掉） |

**验收点**：`PendingDeliverySchedulerTest` 7 个用例（同日跳过 / 隔日重试 / 跨月 /
格式异常 / 空值 / 空格容错）。

## 三、⚠️ 上线前必须做的三件事

1. **确认影刀已停写素材表** —— 因为 `direct-write=true`，两边同时写会互相覆盖
2. **先 dry-run 观察几轮** —— `dingtou.dry-run=true` 时定时任务只算不写、不建计划
3. **再打开定时任务** —— `dingtou.scheduler.pending-enabled=true`

**推荐上线顺序**：
```
① 保持 pending-enabled=false（默认）
② 手动跑一次 processPending 验证（dry-run）
③ 打开 direct-write，确认影刀已停
④ 打开 pending-enabled，cron 先设宽松（如 30 分钟）
⑤ 观察几轮后调紧
```

🔴 **验证中发现并修掉的 3 个问题**：

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | **`code=40002 advertiser does no grant you /qianchuan/aweme/video/get/ permission`** | **token 用错了** —— 我用了千川 token，而老板示例代码用的是**随心推 token**（`sxToken`） | 两个接口（视频列表 / 品名反查）都改用 `suixintuiToken` |

| 3 | 抖音名 **多了个「的」**（`尚尚孕期（努力版）的`） | 正则 `【([^】]+)的?作品】` 里 `的?` 可选 → 被贪婪吃进昵称 | 改成非贪婪 `【(.+?)(?:的作品\|作品)】` |

📌 另外**补上了「抖音名 / 抖音号」**：
- **抖音名** ← 从分享文本抠（`看看【xxx的作品】`）
- **抖音号** ← 数值 uid 用授权达人接口**反查**（`AwemeShowIdResolver.resolveBatch`）
